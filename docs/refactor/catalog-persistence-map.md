# 統合目録の保存基盤（2026-10-07 / Ver1.2.3）

## 実装範囲

`assets/constants/catalog.js` にschema、所蔵先・利用状態、許可フィールドを定義する。`catalog-model.js` は検証と旧本棚の追加移行、`catalog-store.js` は専用IndexedDBの読み取り・移行・JSON往復を担当する。既存のlocalStorage、ファイル用IndexedDB、OPFS、クラウド同期payloadは変更しない。

シリーズ、書籍、所蔵、利用期間、読書イベント、現在の手動状態を別ストアにする。KU返却済み状態と過去読了・再借用・再読進捗を同時に保持できる。巻表示は文字列と整数の並び順で表す。購入とKU借用は別所蔵として同じ書籍へ参照できる。

この段階は保存基盤のみ。アプリ起動時の自動移行、登録・編集・借用返却操作、シリーズ検索画面、D1同期にはまだ接続していない。画面から統合目録を利用できるリリースではない。

## Repository API

`openCatalog()` で開き、`read()`、`migrateLegacy(storage.data)`、`exportJSON()`、`restoreJSON(text)`、`close()`を利用する。時計・UUID・IndexedDB・DB名はテストで注入できる。初期化は将来の目録画面側で行い、既存Readerの初期化順序へ依存させない。

移行は明示的なローカルIDとクラウドIDで重複を抑制する。同名書籍は別レコードのまま残す。Web小説・仮想画像書籍を除外し、形式不明はnull、利用可否はunknownとする。本体ファイルの実在や購入事実を推測しない。後からリンクが確立した場合、ユーザー編集を保持してIDを補完する。別々に目録化済みの所蔵へ同じリンクが付いた場合は、明示的な調整が必要な競合として処理を中止する。

旧進捗・しおり・履歴はこの移行で複製・削除しない。読了日時を古い進捗100%から捏造しない。目録の手動状態との連携は次段階で定義する。

## 保存と復元

JSONにはschemaVersionと全IDを含める。本体・認証情報を保存する項目は設けず、未知の項目・不正参照・重複ID・不正進捗・危険なURLを拒否する。読み込みは利用期間と読書イベントの所蔵一致も確認する。schemaを理解できないバックアップで既存目録を上書きしない。

復元は全目録を置き換える操作。事前検証後、全ストアを同一トランザクションで書き換え、トランザクション完了まで成功を返さない。途中の書き込み失敗ではclearを含む全操作をロールバックする。移行も読み取りから書き込みまで同じトランザクションで行い、複数タブの同時移行が重複を作らないようにする。

現在の書き込みAPIは移行・全体復元用。日常の編集や10,000所蔵での検索には、レコード単位の更新とインデックスを次段階で追加する。ローカルschemaは端末内の目録であり、認証ユーザー別同期・revision競合解決・tombstone伝播は段階Eで実装する。バックアップUIと明示確認は段階C以降で提供する。

## 検証

Nodeで移行の再実行、旧データ不変、同名別書籍、遅延リンク、リンク競合、KUのJSON往復、不正入力を検証する。Chromeの実IndexedDBで同時移行、再オープン、KUの返却状態と読了イベントの永続化、不正復元の拒否、clear後の書き込み失敗による全体ロールバック、旧Readerストレージ不変を検証する。

実行: `node --experimental-vm-modules --test tests/*.test.mjs`、`node tests/catalog-store-browser.mjs`。後者は環境に応じてBROWSER_EXECUTABLEへChromeのパスを指定する。
