# 統合電子書庫目録・読書位置復帰 実装計画

作成日: 2026-10-07。利用者提示の「統合BookReader 開発計画案」と現行コードの調査に基づく。今回の成果物は計画であり、機能実装・デプロイ・Android実機検証は未実施。

## 1. 最優先の完成形

シリーズ名で検索すると、巻ごとに「何を持っているか」「どこで読めるか」が分かり、ローカル書籍を開くか公式サービスへ移動できる。ファイルがこの端末になくても、所蔵記録は残る。

例（架空の所蔵状況）:

| 巻 | 所蔵先・形式 | この端末での操作 |
| --- | --- | --- |
| 1巻 | Local・EPUB | BookReaderで読む |
| 2巻 | Kindle | Kindleの登録リンクを開く |
| 3巻 | U-NEXT | U-NEXTの登録リンクを開く |
| 4巻 | Local・CBZ | ファイルを選び直す |
| 5巻 | Kindle、U-NEXT | 読むサービスを選ぶ |

元案の優先順位を変更する。検索・シリーズ・巻の整理・複数所蔵・データ持ち出しはMVPに含める。読書時間・履歴・統計はMVP後とし、目録の完成を待たせない。Androidの位置維持は独立した先行修正にする。

未登録と未購入は区別する。既刊一覧を取得しないMVPでは、記録のない巻を「未購入」と断定しない。明示的に登録した巻だけ「未所蔵」を設定できる。

## 2. 現行実装と拡張方針

| 領域 | 確認した現状 | 採用方針 |
| --- | --- | --- |
| UI | Vanilla JavaScript / ES Modules、既存ライブラリ、日英表示、PWA | 作り直さず目録画面を追加し、既存読書画面へ接続 |
| 書籍本体 | `assets/fileStore.js` のIndexedDB / OPFS | 現状を維持。新目録DBへ本体を複製しない |
| 読書状態 | `assets/storage.js` のlibrary / progress / bookmarks等、localStorage | 既存ID・進捗・しおりを維持 |
| 既存本棚 | `assets/js/core/sync-logic.js` のbuildLibraryEntries | 新目録は専用の一覧構築処理を使用 |
| 同期 | Firebase認証、Workers、D1のbook_states / user_indexes | 認証と運用環境を再利用、新しい目録同期を追加 |
| 送信制限 | `assets/js/core/cloud-payload.js` の許可項目方式 | 目録専用スキーマを追加。既存schemaへ任意項目を混ぜない |
| テスト | Nodeテスト、browser-smoke、reader-location-cases | 同じテスト基盤へ回帰ケースを追加 |

現行本棚は書名＋著者で表示上の重複をまとめるため、そのまま外部サービスを追加すると複数所蔵が見えなくなる。作品の統合は明示的なID・ユーザー操作で行い、書名一致だけで統合しない。

`provider`はlocal / kindle / unext、`format`はepub / cbz / zip / cbr / rar等として分離する。画像書庫とEPUBは形式であり、KindleとU-NEXTは所蔵先である。既存のWeb小説は既存導線を維持し、購入目録の移行対象からは除外する。

## 3. MVPの操作仕様

1. 既存EPUB・画像書庫を目録へ取り込み、タイトル・著者を引き継ぐ。既存のクラウド目録だけにある書籍も対象とし、形式不明は不明のまま扱う。
2. Kindle / U-NEXTは書名・所蔵先で手動登録できる。シリーズ・巻・公式URL・サービス内IDは後から編集可能。URLなしでも目録として成立し、「リンク未設定」を表示する。
3. 複数選択してシリーズへ所属させ、巻表示と並び順を編集できる。ファイル名からの推定は候補表示のみで、確定前に確認する。
4. 書名・シリーズ名・著者・別名を検索できる。全角半角等は検索用に正規化し、表示用原文を残す。所蔵先・形式・読書状態で絞り込む。
5. シリーズ詳細で巻順に表示する。「上・下」「短編集」「10.5」「合本」「新装版」を数字への強制変換なしで扱う。
6. 同じ巻に複数の所蔵先を追加できる。版違いは別書籍にする。合本は独立書籍とし、通常巻の所蔵へ自動展開しない。
7. Localはファイル実在を確認して開く。ファイル不在時は再選択へ誘導し、識別値で照合する。違う本を選んでも既存進捗へ自動接続しない。
8. Kindle / U-NEXTは登録済みHTTPSリンクをユーザー操作で開く。商品ページと読書用リンクの種別を保持し、商品ページなら「商品ページを開く」と表示する。未確認の独自URLスキームを生成しない。
9. 未読 / 読書中 / 読了と任意の手動進捗を編集できる。外部サービスの進捗不明はnullで保持し、0%と混同しない。リンクを開いただけでは読了や進捗を変更しない。
10. JSON書き出し・復元、CSV一括登録を提供する。CSVはプレビュー、行単位のエラー、重複候補、追加・更新の件数を表示して確定する。

CSV最小列: `title, provider`。追加列: `author, series, volume_label, sort_order, edition, format, provider_book_id, external_url, link_kind, ownership_status`。往復利用するJSONには全IDとschemaVersionを含める。CSVは新規大量登録用で、完全バックアップとはしない。

Kindle / U-NEXTのURLからメタデータを自動取得する処理はMVPに含めない。正しいリンク先への移動は検証するが、特定巻の公式アプリ起動やページ指定復帰はサービス・端末で確認できた組み合わせだけ対応表示する。

## 4. データモデル

元案のbooks.providerを切り離し、「シリーズ → 書籍（巻・版） → 所蔵」を基本構造にする。ASINやローカルファイルIDを作品共通の主キーには使わない。

| エンティティ | 主なフィールド | 意味 |
| --- | --- | --- |
| series | id, name, aliases | シリーズと検索用別名 |
| catalog_books | id, series_id?, title, author?, volume_label?, sort_order?, edition? | 巻・版を識別。seriesなしの単巻も可 |
| holdings | id, book_id, provider, format?, provider_book_id?, external_url?, link_kind?, ownership_status | 一冊に複数所蔵。購入済み・利用期限付き・不明等を区別 |
| local_bindings（端末のみ） | holding_id, local_book_id?, cloud_book_id?, fingerprint?, availability | 既存リーダーと目録を接続。可用性は本体実在で再確認 |
| manual_reading_states | holding_id, status, progress_percent?, source, updated_at | 外部所蔵の手動状態。Localの本文位置は既存progressを参照 |
| reading_sessions（MVP後） | id, holding_id, started_at, ended_at?, duration_sec?, measurement_kind, status, device_id | 所蔵単位の読書記録 |

シリーズ・書籍・所蔵・手動状態のサーバーレコードはすべてuser_id、revision、created_at、updated_at、deleted_atを持つ。IDはUUID、主キーは原則(user_id, id)。手動状態は(user_id, holding_id)。参照制約もuser_idを含め、他ユーザーへの接続を拒否する。時刻はUTCの整数ミリ秒で統一し、表示は端末のタイムゾーンに変換する。

`volume_label`は文字列、`sort_order`は利用者が調整できる整数。巻番号REALだけで表現しない。provider_book_idがある場合の重複検知は(user_id, provider, provider_book_id)で行い、IDのない書籍は書名だけで自動マージしない。URLは識別情報の補助とする。

シリーズ・巻の読了表示は所蔵状態から導出する。同じ巻を両サービスで読了しても冊数は一冊とする。版違いの統計集約は後段で定義し、MVPでは自動的に同一作品へまとめない。

タグ・メモ・表紙はMVP後。必要になった時点でuser_id付きtags / book_tags等を追加する。Statisticsテーブルは最初から持たず、状態とセッションから集計する。

### Kindle Unlimitedの追加要件（MVP必須）

この節は上記モデルとMVP範囲を拡張する。「現在の利用状態」「過去の読書履歴」「現在の読書進捗」を分離し、返却後も履歴を保持する。詳細な時間計測・統計は引き続きMVP後とするが、借用・返却・手動読了の最小履歴はMVPで実装する。

Kindle Unlimitedはprovider=kindle、access_type=subscription_loan、サービス表示名=Kindle Unlimitedとする。通常購入はaccess_type=purchased。同じASINをKUで読んだ後に購入した場合も、購入所蔵を追加してKU履歴を残す。

モデルへの変更:

- holdingsのownership_statusはaccess_typeとavailability_statusへ分割する。availability_statusはactive / returned / expired / unknown等。読書状態の未読・読書中・読了、端末の本体有無とは独立させる。外部状態にはsourceと確認日時を持つ。
- 所蔵の重複検知キーは(user_id, provider, provider_book_id, access_type)へ変更する。購入とKU借用を誤って統合しない。
- access_periodsを追加する。id、holding_id、started_at、ended_at、end_reasonを持ち、再借用は別IDで記録する。最新のreturned_at一つで過去の貸出期間を上書きしない。日時不明はnullとする。
- reading_eventsを追加する。id、holding_id、access_period_id（任意）、event_type、occurred_at、recorded_at、progress_percent（任意）、sourceを持ち、手動読了・進捗等の最小履歴を保持する。現在値はmanual_reading_statesへ反映する。再読開始で現在進捗を戻しても過去の読了イベントは残す。
- 「再読したい」は読了と共存する独立フラグとする。シリーズの過去読了表示は現在の進捗だけでなく読了イベントも参照する。
- 追加エンティティにもuser_id、revision、作成・更新・削除時刻、ユーザーを含む参照制約を適用する。IndexedDB、目録同期、JSONバックアップ・復元へ追加する。CSVのownership_status列はaccess_type / availability_statusへ置き換える。

操作・保存仕様:

1. 借用開始・返却は手動で登録できる。返却は利用期間を閉じて所蔵状態を更新する操作であり、書籍・進捗・読了・読書イベントを削除しない。「42%で返却」「読了後に返却」の両方を残す。
2. 利用期間と所蔵状態、読書イベントと現在進捗はそれぞれ同一トランザクションで保存する。同期も同じmutationIdを持つ一操作として扱い、再送で履歴を増やさない。返却は対象の利用期間IDを指定し、新しい借用期間を誤って閉じない。
3. 本棚に「今利用できる（登録情報上）」と「過去に利用した」の絞り込みを設ける。シリーズ詳細では返却済みも表示する。返却済みKUしかない巻は「KU返却済み・再利用を確認」と表示し、購入所蔵があればそちらを読む候補にする。
4. 外部状態はMVPでは利用者が登録・更新する。未確認の状態を公式サービスで検証済みと表示しない。将来の取り込みでも、Amazonの本棚に見当たらないことだけを根拠に記録を削除しない。
5. 「2026年10月にKUで読了」はKU所蔵に結び付いた読了イベントのoccurred_atで検索する。登録日・返却日を読了日として代用しない。過去日時が不明なら未設定で残す。
6. 履歴は自動期限切れで削除せず、明示削除は別操作とする。同期とバックアップで保全し、端末データ消去にも無条件で残る「永久保存」は約束しない。

受入例: 10月1日借用 → 3日42% → 5日読了 → 6日返却でも、10月のKU読了記録が残る。再借用・再読・購入後も初回の読了日時と借用期間は変わらない。二端末で返却操作を再送しても重複せず、オフラインの返却・再借用競合はrevision競合として解決する。

段階Bにモデル・保存、Cに手動借用／返却、Dに絞り込み、Eに同期、Fに履歴の復元試験を追加する。追加工数は2〜3作業日を見込み、後述の基礎見積もりに加算すると目録MVPは14〜22作業日、位置修正込みで17〜27作業日となる。

Amazonの過去KU履歴・進捗の自動取得可否は未調査。公式手段の最新仕様確認を将来の調査項目とし、取得できない場合も手動記録で上記要件を満たす。

## 5. 保存・同期・移行

### ローカル保存

目録は専用IndexedDBに格納する。series / books / holdings / manualStates / bindings / outbox / migrationsのストアを持ち、目録変更とoutbox追加を同一トランザクションで確定する。目録が増えても既存localStorageの全体書き換えを増やさない。

未ログインでも検索・登録・編集・バックアップが可能。同期は既存の認証設定を利用し、ローカル保存の成功とクラウド同期の成功を別表示する。複数アカウントはデータ領域・outboxを分離する。未ログインの目録を初めてアカウントへ結び付ける際は対象件数を提示し、別アカウントへ黙って転送しない。

### D1/API

既存のbook_states / user_indexesを改造・置換せず、新しいcatalog系テーブルと同期ログを追加する。KVはキャッシュ用途に限定し、読書セッションの正本にしない。

MVPの外部APIは既存のPOST同期方式に合わせ、次の2本を先に実装する。画面側のCRUDはローカルrepositoryが担当するため、元案のREST一式はまだ不要。

| API | 入力 | 出力・責務 |
| --- | --- | --- |
| POST /sync/catalog/pull | idToken, cursor?, limit | ユーザー別変更列、削除記録、nextCursor、hasMore |
| POST /sync/catalog/push | idToken, mutations[] | 各変更のaccepted / conflict / invalid、確定revision |

mutationはmutationId、entityType、entityId、baseRevision、operation、payloadを持つ。認証済みuidをサーバー側で採用し、クライアントのuser_idは信用しない。同じmutationIdの再送は同じ結果を返す。revision競合は409相当の項目結果で返し、同一レコードの両編集を保存して利用者に選択させる。端末時計のみの最終更新勝ちにしない。

サーバーでは変更と単調増加の変更番号をトランザクションで記録し、cursorで差分取得する。初回同期のページング中に追加更新されても抜け落ちないことをテストする。削除はtombstoneで伝え、MVPでは同期ログの破棄を行わない。大量化した時点でcursor期限と全量再同期を追加する。

既存のcloud-payloadへ項目を足すだけでは目録は保存されない。目録専用validator・payload sanitizer・Worker処理を対で追加する。外部URLはサービスの許可ホスト・HTTPS・長さを検査し、認証付き一時URLを同期対象にしない。書籍本体・本文断片・ローカルパス・Amazon/U-NEXT認証情報は送信しない。

### 移行順序と復旧

1. 現在のJSONバックアップを取得できる状態を維持し、移行前に退避を案内する。
2. libraryとcloudIndex、bookLinkMapから候補を作る。既存IDとの対応表を保存し、再実行しても同じ書籍を増やさない。
3. 明示的にリンク済みのローカル・クラウド項目だけ統合する。タイトル一致だけの候補は別件で取り込み、後で統合・分離できるようにする。
4. 旧進捗・しおり・ファイルには触れず、所蔵のbindingから参照する。クラウドだけにある本はこの端末の本体なしと表示する。
5. 新規ファイル登録時は既存の登録成功後に目録側へ冪等で反映する。途中失敗は次回の照合で修復する。
6. 旧本棚も当面利用可能にする。新目録を無効化すれば元の読書導線へ戻れる。新旧UIのファイル削除・書籍削除が互いに壊れないよう回帰検証する。
7. 「端末の本体を削除」と「目録から所蔵を削除」を別操作にする。目録削除だけで進捗や本体を連鎖削除しない。

JSON復元はschemaVersion検証・プレビュー・トランザクションで実行し、失敗時は既存データを維持する。初期版は追加・明示更新方式に限定し、全置換は実装しない。同期を含む復元ではrevisionを新しい変更として扱い、削除済み項目の復活は利用者が選択した場合だけ行う。

## 6. Providerの実装範囲

既存の`init(config)`依存注入方式に合わせてprovider registryと3つの小さなadapterを追加する。

共通操作はvalidateHolding、getCapabilities、getOpenActionに絞る。capabilitiesはlocalRead、externalLink、manualProgress、automaticProgress等の可否を示す。Kindle / U-NEXTのautomaticProgressはfalseとする。未実装のgetProgressが0%を返す設計にはしない。

LocalAdapterはbindingを解決して既存のファイル起動処理へ渡す。外部adapterは検証済みリンクと表示文言を返し、UIのクリックで開く。起動を試みた日時はlastLaunchAttemptAt、実際に読んだ日時はlastReadAtとして分ける。外部起動の成功や読書開始をリンククリックだけで確定しない。

公式ログインは公式画面に任せる。WebView埋め込み・DOM解析・ブラウザ拡張・DRM操作はMVPの依存にしない。

## 7. Android EPUBの読書位置：現状の問題候補

以下は静的コード調査で確認した実装であり、利用者の端末で発生した原因の断定ではない。

| 箇所 | 確認した挙動 | 修正・検証対象 |
| --- | --- | --- |
| app.js: shouldPersistLocalProgress / handleProgress | 保存を進捗率0.1ポイント差で判断 | 同じ表示パーセントのまま本文位置が変わる場合も保存 |
| app.js: visibilitychange | autoSyncEnabledがfalseなら即return | 未ログイン・同期OFFでもhidden時のローカル保存を実行 |
| app.js: pagehide | 保存＋同期経路はある | pagehideだけを頼りにしない |
| app.js: visible後の同期 | 2秒後にpull、resolve、reader.goTo | DOMが生存している復帰で古い保存位置へ動かさない |
| app.js: handleProgress | saveCurrentProgressにあるloading / resolving / repaginationのガードがない | 初期描画・復元中のイベントが通常の読書位置を書き換えないよう統一 |
| reader.js: _getCurrentScrollSegment | テキストの親要素の矩形で判定し、そのノード先頭のsegmentを返す | 長い段落内の読み位置をRange等で捕捉。段落先頭への巻き戻りを検証 |
| reader.js: getPageLocator等 | 0位置を過去の有効値で補う | 本当に先頭へ戻した操作と、非表示中の計測失敗を区別 |
| reader.js: スクロール位置取得 | 結合DOMの走査とpage.spineIndexを組み合わせる | 実際に見えているspineの識別と区間番号の対応を検証 |
| sync-logic.js: resolveSyncedProgress | 1%以上は選択、未満は更新時刻等で解決 | 1%未満でも本文では大きな差になる。復帰時の生存位置・未保存変更を保護 |

Chromeのライフサイクル説明では、モバイルのhidden移行は最後に観測できる機会になり得て、pagehide等が来ない終了もある。したがって保存は平常時とhidden時に完結させ、終了時のネットワーク完了を必須にしない。参考: [Chrome Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。

## 8. 読書位置の確定仕様

### 位置の正本

進捗率は表示用。EPUB復元の正本は書籍識別値＋spineIndex＋本文内の細かな位置とする。現行segmentIndexとの互換を維持し、必要に応じてversion付きanchorに文字オフセット・画面内相対位置を追加する。段落が複数画面にまたがる場合にも、見えている行を捕捉する。

ローカルanchorはviewportOffsetと既存のvisibleTextによる補助を持てる。章内比率は正確なanchorが解決できない場合の補助にする。旧データは従来のsegmentで復元し、新形式へ段階移行する。別版へ本文位置を自動転用しない。

新しい位置項目を端末間同期する場合は、クライアント／Worker双方の許可schemaとSYNC_DATA_POLICYを同じリリースで更新する。本文断片は引き続き端末内だけとする。

### 保存

- 可視・レイアウト有効・復元中でない状態で最後の有効anchorをメモリへ更新する。
- 位置変化を基準に保存し、パーセント差を必須にしない。初期設定案はスクロール停止後300ms、連続スクロール中は最大1秒ごとのローカルcheckpoint。定数へ集約し、実測負荷で調整する。
- hidden / pagehideはクラウド設定に関係なく最後の有効checkpointをローカルへflushする。隠れたDOMを再計測して0や章先頭で上書きしない。
- 軽量な書籍別checkpointを保存し、毎秒library全体をシリアライズしない。通常の既存progressへ統合するときもcheckpointの新旧を考慮する。
- ユーザーの先頭移動・戻る操作は正しい更新として保存する。進捗の最大値を残す方式は使わない。
- 保存失敗時は最後の成功記録を維持し、保存できていない状態を通知する。成功していない書き込みを「保存済み」にしない。

### 復帰

1. 同一DOM・同一レイアウトが残っている: 現在のスクロール位置を維持する。無条件のgoToを行わない。
2. DOMが残り、回転やviewport変更がある: 非表示前のanchorを使い再配置する。本文・画像・フォントのレイアウト安定後に画面内位置を補正する。
3. OSがページを破棄・再読み込みした: 書籍識別後、最新の永続checkpointを復元する。復元完了までは進捗更新を保存しない。本体がなければ再選択後に復元する。
4. 復帰後のクラウド取得: 最新ローカルanchorと編集世代を先に確保する。応答到着までに読書が進んだら、その応答で画面を移動しない。同じ位置ならジャンプしない。
5. 別端末の異なる位置: 同じ本を画面で読んでいる最中は「別端末の続きへ移動」の明示操作で切り替える。既存の1%差ダイアログとの重複を整理し、通常の書籍起動時の同期選択は維持する。
6. 復元に失敗: 同じ章の近傍等のfallbackを表示し、精密な保存位置を低精度の結果で即上書きしない。

診断時はbookId、anchor、保存理由、保存成功、編集世代、visibility、同期適用理由を端末内で記録する。本文や認証情報はログへ含めない。

### 受入試験

Android Chrome・インストールPWAを必須とし、配布APKは別環境として確認する。実機はPixelを優先。PCの疑似visibilityテストだけでは完了にしない。

- 短い段落／数画面にまたがる長い段落／画像入り／結合spine境界／章末／最終章。
- スクロール直後、停止後、30秒・5分のアプリ切替、画面ロック、回転、OSによる破棄後の再読込。
- 同期OFF、未ログイン、オフライン、同期ON、遅い応答、別端末更新、復帰後すぐの読書操作。
- 先頭へ明示移動、逆方向スクロール、目次移動、文字サイズ変更、書籍切替中の古いイベント。
- 同一レイアウトで通常復帰した場合、同じ本文行と画面内位置を維持する（目標誤差1行以内）。再レイアウト時は同じ本文箇所が画面内にある。
- 500ms以上停止して通常切替したケースでは停止位置を復元。予告なしのプロセス終了では最後に成功したcheckpointへ戻る（平常時の目標は1秒以内の記録間隔。OS停止時の完全保存は保証しない）。
- 100回の通常切替試験で章先頭や数画面前への巻き戻り0件。テスト用の既知anchorと前後画面で判定する。

## 9. MVP後の読書履歴・時間計測

外部アプリ起動からBookReader復帰までの時間には、他アプリ操作や放置が含まれる。PWAだけでKindle / U-NEXTの実際の読書時間・終了・進捗を確定できる設計にはしない。

Localは表示中の読書セッションを記録し、hiddenで停止する。無操作時間の扱いは設定し、表示時間としての定義を明示する。外部は起動時にpendingセッションを残し、復帰後に利用者が時間を確認・修正・破棄できる。戻らなかった記録はpendingのままにして、自動で一晩分を加算しない。

measurement_kindをlocal_visible / external_estimated / manual等に分け、未確定の外部推定時間は実読書時間に混ぜない。セッション開始・終了は同じsessionIdで冪等にし、複数タブ・端末の重複時間は合算ルールを定義する。

開始日時・終了日時・累計・閲覧回数・最終閲覧は確定した記録から計算する。日時は「初めて読んだ日時」「直近セッションの日時」「初回読了日時」を区別する。統計はこの仕様の成立後に日・月・所蔵先別へ拡張する。

## 11. リリース判定と保留事項

MVPの必須判定:

- EPUB・画像書庫・Kindle・U-NEXTが混在するシリーズを検索し、巻単位で所蔵先と操作を選べる。
- 同巻複数所蔵、同名別版、外伝、上・下、合本、巻番号不明が欠落せず表示される。
- 既存の進捗・しおり・ファイルを維持し、画像書庫・EPUB・Web小説の既存動作が通る。
- 10,000所蔵のテストデータで検索と一覧を測定する。初期目標は検索反映300ms以内。全件DOM生成を避け、ページングを採用する。基準端末と測定結果を記録する。
- 不正CSV・不正URL・重複インポート・保存容量不足・同期失敗で既存データを失わない。
- ローカルとクラウドのどちらから登録しても、2端末で所蔵の追加・編集・削除が収束する。
- JSONバックアップから件数・ID・シリーズ・所蔵・手動状態が復元できる。本体ファイルはバックアップ対象外と明示する。

未確定事項はMVPの妨げにしない。Kindleの個別Readerリンク、Android公式アプリへの遷移、U-NEXTの個別巻リンクは実装段階で利用者が登録した実例をWindows / Androidで検証し、対応可否を記録する。公式の購入履歴API・エクスポート・自動取り込みは別の調査課題とする。

U-NEXTは公式ヘルプでアプリ・ブラウザの購入済み本棚の導線を案内しているが、このことは個別巻のアプリ直起動を保証しない。参考: [U-NEXT「本棚を確認・整理したい」](https://help.unext.jp/guide/detail/bookshelf)。

次の実装はAから開始し、その後B〜Dで「どの巻をどこで持っているか」が分かる状態を先に作る。DOM解析・読書時間の自動取得・統計画面は、この成立条件に含めない。
